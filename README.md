# codyssey_mini_npu

## 프로젝트 개요
AI가 계산하는 방식(MAC: Multiply-Accumulate)을 흉내 내는 작은 콘솔 계산기, **Mini NPU Simulator**입니다. 패턴과 필터를 같은 위치끼리 곱해서 모두 더한 점수로 패턴이 십자가(Cross)인지 X인지 판정합니다.

- 언어: Python 3.8 이상 (표준 라이브러리 `json`, `time`만 사용, NumPy 같은 외부 라이브러리 없음)
- 구조: `main.py` 하나에 기능별 함수로 나눔 (MAC, 판정, 라벨 정규화, 성능 측정, 패턴 생성 등)

## 실행 방법
```bash
git clone https://github.com/hunyhan/codyssey_mini_npu.git
cd codyssey_mini_npu
python main.py
```
- Python 3.12.10에서 확인했습니다.
- 모드 2는 `data.json`을 읽으므로 프로젝트 폴더(`main.py`와 `data.json`이 있는 곳)에서 실행해야 합니다.

## 기능 목록
| 모드 | 입력 | 기능 |
|---|---|---|
| 1. 사용자 입력 (3x3) | 필터 A, 필터 B, 패턴을 각각 3줄씩 (한 줄에 숫자 3개, 공백 구분) | A, B 점수와 연산 시간(10회 평균)을 보여 주고 점수가 큰 쪽으로 판정합니다. 3x3 성능 표도 출력합니다. |
| 2. data.json 분석 | 없음 (`data.json`을 읽음) | 필터를 크기별로 불러와 패턴 6개를 판정하고 PASS/FAIL, 크기별 성능 표, 결과 요약을 출력합니다. |
| 3. 패턴 생성기 (보너스) | 크기 N (3 이상 홀수) | N×N 십자가와 X 패턴을 만들어 ■□로 그리고, MAC 점수와 성능 표를 보여 줍니다. |

모드 1 예시
```
필터 A: 0 1 0 / 1 1 1 / 0 1 0   (십자가)
필터 B: 1 0 1 / 0 1 0 / 1 0 1   (X)
패턴  : 0 1 0 / 1 1 1 / 0 1 0   (십자가)

A 점수: 5.0
B 점수: 1.0
판정: A
```

입력 처리
- 메뉴에서 1, 2, 3이 아닌 입력은 안내 후 다시 묻습니다.
- 행렬 입력에서 숫자 개수가 다르거나 숫자가 아니면 `입력 형식 오류`를 보여 주고 그 줄을 다시 받습니다.
- 패턴 생성기에서 숫자가 아니거나 3 이상 홀수가 아니면 다시 묻습니다.
- `data.json`이 없거나 JSON 형식이 깨졌으면 `data.json을 읽을 수 없습니다: …`를 보여 주고 종료합니다.
- `Ctrl+C`나 입력 끊김(EOF)이면 `입력이 중단되었습니다. 프로그램을 종료합니다.`를 보여 주고 종료합니다.

## 데이터 파일 (data.json)
- 경로: 프로젝트 폴더의 `data.json` (UTF-8)
- 역할: 크기별 필터(5×5, 13×13, 25×25)와 판정할 패턴 6개, 각 패턴의 정답(`expected`)
- 필드 구조

```json
{
  "meta": { "version": "1.0", "type": "json" },
  "filters": {
    "size_5": { "cross": [[...], ...], "x": [[...], ...] }
  },
  "patterns": {
    "size_5_1": { "input": [[...], ...], "expected": "x" }
  }
}
```

| 필드 | 뜻 |
|---|---|
| `filters` | `size_N` 키 아래에 N×N 필터 두 개 (`cross`, `x`) |
| `patterns` | `size_{N}_{idx}` 키마다 N×N 패턴(`input`)과 정답 라벨(`expected`) |

- 키 규칙: `size_13_2`에서 `split("_")[1]`로 크기 13을 꺼내 `size_13` 필터와 비교합니다.
- 라벨 정규화: 데이터에는 `cross`, `+`, `x`처럼 표기가 섞여 있어서 `+`, `cross` → `Cross`, `x` → `X`로 맞춘 뒤 비교합니다. (대소문자, 앞뒤 공백 무시)

## 구현 요약
| 기능 | 함수 | 설명 |
|---|---|---|
| MAC 연산 | `mac()` | 이중 반복문으로 `pattern[i][j] * filter[i][j]`를 모두 더함 |
| 판정 | `judge()` | 두 점수 차이가 `EPSILON = 1e-9`보다 작으면 `UNDECIDED`(동점), 아니면 큰 쪽 |
| 라벨 정규화 | `normalize_label()` | `+`, `cross` → `Cross`, `x` → `X`. 모르는 라벨은 `None` |
| 필터 로드 | `load_filters()` | 크기별로 필터를 읽고 라벨을 정규화해 저장 |
| 패턴 판정 | `analyze_pattern()`, `is_square()` | 키 형식 오류, 그 크기 필터 없음, 패턴이 N×N 아님, expected 라벨 오류를 FAIL 이유로 기록하고 다음 케이스를 계속 처리 |
| 시간 측정 | `measure_mac_ms()` | `time.perf_counter()`로 10회 반복한 평균을 ms로 표시 |
| 결과 요약 | `print_summary()` | 총 테스트, 통과, 실패 수와 실패 케이스 목록·이유 |

보너스
- **보너스 1, 1차원 최적화**: `flatten()`으로 N×N 2차원 리스트를 길이 N²인 1차원 리스트로 펴고, `mac_flat()`이 반복문 하나로 `k`번째끼리 곱해 더합니다. 펴는 시간은 측정에서 빼고, 같은 입력과 같은 반복 횟수로 2차원과 1차원 시간을 성능 표에 나란히 보여 줍니다.
- **보너스 2, 패턴 생성기**: `make_cross(N)`은 가운데 줄과 가운데 칸(`i == N // 2` 또는 `j == N // 2`)을 1로, `make_x(N)`은 두 대각선(`i == j` 또는 `i + j == N - 1`)을 1로 채웁니다. 모드 3에서 ■□로 그려 보여 주고, 성능 표의 테스트 데이터로도 씁니다.

## 결과 리포트

### 모드 2 실행 결과
| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL (동점 규칙) |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL (동점 규칙) |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL (동점 규칙) |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

총 테스트 6개, 통과 3개, 실패 3개입니다.

### 실패 원인 분석
1. 실패한 3개(size_5_1, size_13_2, size_25_1)는 모두 이유가 `동점 규칙`으로 같습니다.
2. 세 케이스 모두 두 점수 차이가 1e-16 ~ 3e-15 정도(0.000000000000003 이하)로, `EPSILON(1e-9)`보다 훨씬 작아서 `UNDECIDED`로 판정되었습니다.
3. 이 작은 차이는 부동소수점 오차입니다. 컴퓨터는 0.1 같은 소수를 2진수로 정확히 저장하지 못해서 `0.1 + 0.2`가 `0.30000000000000004`가 되는 것처럼, 같아야 할 합이 끝자리에서 조금 달라집니다.
4. 즉 두 점수는 사실상 같은 값이고, 오차 때문에 생긴 끝자리 차이로 승부를 정하지 않도록 동점 정책을 둔 것이 그대로 동작한 결과입니다.
5. 실패 원인을 세 가지로 나누면 다음과 같습니다.
   - 데이터/스키마: 키 형식, 필터 크기, 패턴 크기, expected 라벨을 검사하지만 이번 실행에서는 걸린 케이스가 없습니다. `+`, `cross`, `x` 라벨은 정규화로 모두 통과했습니다.
   - 로직: 판정이 expected와 다른 `판정 불일치`는 0개입니다. 점수 차이가 분명한 3개는 모두 맞게 판정했습니다.
   - 수치: 실패 3개 모두 여기에 해당합니다. 부동소수점 오차 + epsilon 동점 정책 때문입니다.
6. expected가 X나 Cross로 정해져 있어도, 점수가 같은 패턴은 이 프로그램의 정책상 어느 한쪽으로 정하지 않는 것이 맞다고 보고 정책을 바꾸지 않았습니다.

### 성능 분석과 시간 복잡도
모드 2 성능 표 (평균/10회, [최종 실행 화면](docs/14-final-run.md)의 값. 실행할 때마다 값은 조금씩 다릅니다)

```
크기         2차원(ms)     1차원(ms)    연산 횟수
--------------------------------------------------
3x3              0.001         0.001             9
5x5              0.001         0.001            25
13x13            0.007         0.005           169
25x25            0.024         0.019           625
```

1. MAC은 N×N 칸을 한 번씩 곱하고 더하므로 연산 횟수가 N²이고, 시간 복잡도는 **O(N²)**입니다.
2. 크기가 13에서 25로 약 2배가 되면 연산 횟수는 169에서 625로 약 3.7배가 되고, 2차원 시간도 0.007 ms에서 0.024 ms로 약 3.4배 늘었습니다. 크기의 제곱에 맞춰 시간이 늘어나는 것을 확인할 수 있습니다.
3. 3x3, 5x5는 시간이 너무 짧아서 반올림 때문에 차이가 거의 보이지 않습니다. 크기가 커질수록 O(N²) 경향이 더 잘 보입니다.
4. 1차원 MAC도 곱셈 횟수는 N²로 같아서 시간 복잡도는 똑같이 O(N²)입니다.
5. 그래도 25x25에서 0.024 ms → 0.019 ms로 1차원이 조금 빠릅니다. 값을 꺼낼 때 `pattern[i][j]`(줄을 찾고 칸을 찾음) 대신 `pattern_flat[k]`(한 번에 찾음)를 쓰고 반복문도 하나라서, 연산 수는 같고 접근 방법만 단순해졌기 때문입니다.
6. 실제 NPU가 큰 행렬을 빠르게 처리하는 이유도 이처럼 같은 MAC을 아주 많이 반복하는 일을 하드웨어로 한꺼번에 처리하기 때문입니다.
